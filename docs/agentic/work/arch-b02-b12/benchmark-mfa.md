# Décision documentaire MFA — 2026-10-11

## Verdict et recommandation

**NO GO pour le plugin MFA natif Better Auth 1.7.7, à exigences inchangées.** Cela concerne le mécanisme natif examiné, pas une impossibilité de la bibliothèque entière. La dernière release stable officielle reste v1.7.7, publiée le 30 septembre 2026 ; aucun nouveau contrat natif de secours hashés n’est donc identifié.

**Recommandation : proposer Keycloak 26.8.0 auto-hébergé comme alternative d’architecture prioritaire, sans adopter le changement aujourd’hui.** Il corrige réellement le stockage récupérable des codes de secours et apporte une protection optimiste des credentials ; il n’est pas un GO complet DossierClé. Deux conditions restent déterminantes : protection du secret TOTP conformément à D54 et qualification de consommation simultanée/transaction avant création effective de sessions. La source permet une recommandation conditionnelle, pas un PASS runtime.

Une simple substitution Authentik/Kratos ne résout pas l’exigence. ZITADEL est une alternative secondaire avec meilleur chiffrement TOTP natif mais une réserve de concurrence visible et un arbitrage licence AGPL/commerciale. Aucun candidat alternatif n’est déclaré conforme à toutes les exigences sans reste. Le STOP POC demeure : cette étude ne propose aucune reprise automatique ni essai préalable imposé.

## Contraintes préservées

D01/D02 : e-mail+mot de passe, TOTP obligatoire avant métier, secours à usage unique, pas SMS/e-mail ni trusted-device de substitution. D03/D04 : invitation seule, pas inscription publique ni création automatique d’agence. D05 : perte des deux facteurs nécessite contrôle humain d’identité, accord admin/propriétaire, lien temporaire, révocation et audit. D10/D11/D60 : cookie sécurisé opaque, session serveur, révocation actuelle, idle 30 minutes d’activité humaine réelle et absolu 15 jours ; polling/refresh exclus. D54/ADR003 : identité centrale, mot de passe hashé, TOTP chiffré avec clé hors DB ; secours irréversibles, consommation atomique, aucun réaffichage/export/log. D71 adopte Better Auth de principe sans annuler ces exigences ni donner un PASS ; changement de fournisseur exige un ADR proposé et validation humaine.

### Better Auth : qualification précise

Le tag v1.7.7 résout le commit `db02f233918ad1233bf0753e437e1c0da353273d`. Dans backup-codes/index.ts, storeBackupCodes supporte plain/encrypted ou custom encrypt/decrypt ; decode doit produire une liste de codes et verify utilise includes(code brut). La fonction viewBackupCodes est serverOnly : elle n’est **pas un endpoint HTTP public**, mais confirme la récupérabilité côté serveur. L’update de consommation vérifie l’état précédent (CAS) : ce point n’est pas rejeté ; il ne transforme pas les codes en hashes et reste sans preuve runtime. Un faux encrypt/decrypt qui renvoie un hash n’est pas une extension supportée de vérification. Aucun plugin officiel exact identifié ajoutant un contrat hash/comparator/consume irréversible. Une extension officielle future pourrait rouvrir ce NO GO après nouvelle étude, sans promettre son existence. [Source immutable](https://github.com/better-auth/better-auth/blob/db02f233918ad1233bf0753e437e1c0da353273d/packages/better-auth/src/plugins/two-factor/backup-codes/index.ts), [release stable](https://github.com/better-auth/better-auth/releases/tag/v1.7.7).

### Keycloak : pourquoi le retenir, ce qu’il ne faut pas annoncer

Tag 26.8.0, commit `4246609cf2024c85016d3fb1254c3d2533367c31`, publié le 1 octobre 2026. Le modèle construit réellement SHA512(rawCode), stocke les hashes en Base64 et le provider retire le prochain hash après vérification. Le digest rapide n’est pas un hash de mot de passe : les codes sont aléatoires dans un un alphabet de 34 symboles, avec 12 caractères, soit environ 60 bits d’entropie par calcul ; pas de sel par code visible dans cette fonction. Les codes doivent être utilisés dans l’ordre, impact UX à montrer. Le modèle CredentialEntity porte @Version, protection optimiste de concurrence ; confirmer que le conflit empêche le second succès avant émission de session sur deux instances est une preuve de livraison, pas un résultat acquis. Les recovery codes sont supported depuis 26.3. [Hashes](https://github.com/keycloak/keycloak/blob/4246609cf2024c85016d3fb1254c3d2533367c31/server-spi/src/main/java/org/keycloak/models/credential/RecoveryAuthnCodesCredentialModel.java), [algorithme](https://github.com/keycloak/keycloak/blob/4246609cf2024c85016d3fb1254c3d2533367c31/server-spi/src/main/java/org/keycloak/models/utils/RecoveryAuthnCodesUtils.java), [provider](https://github.com/keycloak/keycloak/blob/4246609cf2024c85016d3fb1254c3d2533367c31/services/src/main/java/org/keycloak/credential/RecoveryAuthnCodesCredentialProvider.java), [version JPA](https://github.com/keycloak/keycloak/blob/4246609cf2024c85016d3fb1254c3d2533367c31/model/jpa/src/main/java/org/keycloak/models/jpa/entities/CredentialEntity.java), [release/support](https://www.keycloak.org/docs/26.4.7/release_notes/index.html).

**Réserve TOTP supplémentaire :** OTPCredentialModel sérialise le secret dans secretData ; aucun chiffrement applicatif natif de ce champ identifié. La documentation recommande chiffrement des volumes/DB, WAL et backups, qui ne protège pas automatiquement un dump SQL en clair ni contre lecture SQL autorisée. Ne pas assimiler cette protection physique à l’enveloppe chiffrée clé hors DB/backup de B07. Deux voies documentaires : établir une protection native/supportée satisfaisant cette frontière, ou proposer explicitement dans l’ADR une interprétation/arbitrage de D54 par protection DB+WAL+backups à clés séparées avec limites visibles. Sans cette résolution, Keycloak n’a pas de GO global à exigences inchangées. Aucun provider cryptographique maison proposé. [Modèle TOTP](https://github.com/keycloak/keycloak/blob/4246609cf2024c85016d3fb1254c3d2533367c31/server-spi/src/main/java/org/keycloak/models/credential/OTPCredentialModel.java), [protection repos recommandée](https://www.keycloak.org/server/db).

### ZITADEL : intérêt et risque restant

Tagv4.19.4 commit `101343ad87aef7b0eea7c3522d519308e0ea9547`, publié le 1 octobre 2026. ## Proposition concrète d’architecture, pas adoption

Préparer ADR003 de remplacement **PROPOSED** : Keycloak central comme fournisseur d’identité, serveur NestJS REST conservé et navigateur React gardant uniquement cookie opaque. OIDC Authorization Code+PKCE géré par backend ; tokens restent côté serveur. Session application centrale vérifiée à chaque requête, appartenance/droits courants DossierClé conservés, aucun organization plugin fusionnant agence et identité. Déconnecter/révoquer localement immédiatement ; intégration logout/backchannel et état IdP sans cache d’autorisation permissif. Pas validation JWT hors ligne comme preuve de révocation immédiate. IdP down => refus métier.

Configurer TOTP et secours comme obligations de première activation avant métier, registration désactivée, invitations exclusivement DossierClé et APIs admin privées à compte service minimal. Récupération D05 demeure un workflow humain app audité, sans bouton email seul qui retire MFA. Tout réenrôlement invalide anciennes sessions et facteurs/codes ; prévenir réapparition après restore. Idle humain/absolu 15 jours restent sous contrôle app : réglages SSO ne prouvent pas que polling ne prolonge pas la session.

Coût : Keycloak Apache 2.0 n’impose pas une licence par utilisateur dans cette distribution communautaire, mais hébergement+DB+backups/HA+patchs+astreinte+support sont à payer. Ni 0 € en production ni chiffrage cloud inventé. Runtime Java persistant central + PostgreSQL et cache/clustering ajoute un service d’exploitation et doit être réconcilié avec contrainte managé/serverless/B04 ; Scaleway UE est un lieu de déploiement possible, pas un service Keycloak managé attesté. Version/digest, licence, capacité, topologie UE, contrat support et PRA restent à fixer. ZITADEL ajoute licence AGPL/revue ou contrat commercial, pas présumé gratuit pour toutes modalités.

## Conditions de décision et de livraison

Pour choisir l’alternative : valider ADR proposé et frontend/backchannel frontières ; résoudre explicitement secret TOTP, exploitation persistante et responsabilité/coût. Aucun humain n’a approuvé ce remplacement dans ce rapport. Si ces conditions ne peuvent être documentées, maintenir NO GO MFA plutôt que développer un plugin cryptographique maison ou relâcher les secours.

Pour livrer les stories auth, prouver dans Execute/Verify autorisés ultérieurement : jamais accès métier avant MFA ;20 soumissions simultanées même code sur 2 instances ⇒ 1 seule session ; anciens codes invalides après regeneration ; absence réaffichage/export/log/dump récupérable selon protection décidée ; clé TOTP absente sauvegarde ; révocation compte/rôle/session immédiate ; idle humain avec polling ; reset contrôlé dernier admin ; restore ne ressuscite pas facteurs/droits. Ces critères sont des preuves de livraison, pas un nouveau POC demandé maintenant.
